What this is

An automotive product-security portfolio, engineered to a specification

One repository, six projects, each covering a different slice of the lifecycle: threat analysis, secure boot, key management, in-vehicle communication security, network defence, and firmware validation.

Each project ships as a complete engineering package before a line of code exists — a technical specification, a phased build plan, and a definition of done that has to pass before the project counts as finished. That is deliberate. Writing the spec first is what separates “I built a thing” from “I engineered a thing to a requirement and can prove it met one.”

Read this part first

Everything here is a simulation. These projects model hardware behaviour in software. They do not touch an ECU, a transceiver, a real HSM, or a vehicle. Nothing here is AUTOSAR-conformant, ISO-certified, independently reviewed, or production-grade.

That sentence is at the top on purpose, not buried in a footnote, because the alternative is having an interviewer find the gap themselves. Five capabilities — logic analyzer, JTAG, oscilloscope, CANoe, and physical CAN hardware — need real hardware, so nothing here claims them. The rule is executable: the repository’s own validation tool fails the build if a project claims one.

The six projects

Each one has a demo that lands

Listed in recommended build order. Every project links to its own specification, phased build plan, and interview talking points.

PROJECT 01

Secure Boot Chain Simulator

BootROM → bootloader → application, each stage cryptographically verifying the next. Hardware root of trust in OTP fuses, an HSM that never releases a private key, monotonic anti-rollback counters, and measured boot with a PCR bank.

The demo that lands. An image with a valid signature from the legitimate signing key that the chain still refuses to boot, because its security version number sits behind the monotonic counter.

Python 8 phases · 17 criteria · a long weekend
PROJECT 02

CAN Bus SecOC Demo

AUTOSAR Secure Onboard Communication over a virtual CAN bus: AES-128 CMAC authenticators, truncated MAC and truncated freshness value, receiver-side freshness reconstruction with an acceptance window, and resynchronisation.

The demo that lands. The same replay attack, twice. Unprotected, the receiver actuates on a stale brake command. Protected, the identical bytes are rejected — with the freshness window that was searched printed on screen.

Python 9 phases · 17 criteria · a long weekend
PROJECT 03

ECU Key Lifecycle Manager

The full cryptographic key lifecycle for a simulated fleet: HSM generation, HKDF derivation, a challenge-response provisioning ceremony bound to one ECU, rotation with an overlap window, signed revocation lists, and a hash-chained audit log.

The demo that lands. Tamper with one byte of the audit log, live, and have the tool name the exact sequence number that broke the chain.

Python 10 phases · 19 criteria · a week of evenings
PROJECT 04

ISO/SAE 21434 TARA Workbench

The Clause 15 TARA workflow as version-controlled structured data rather than a spreadsheet — computed risk determination, a thirteen-rule linter, and bidirectional traceability from any requirement back to the asset it protects.

The demo that lands. A complete worked TARA for an OTA telematics gateway ECU, passing its own linter in CI, with requirements that trace into the other projects’ test cases.

Python 9 phases · 17 criteria · a week of evenings
PROJECT 05

In-Vehicle Network Security Lab

Three protocols — LIN sub-bus, CAN-FD backbone, Automotive Ethernet with SOME/IP-SD and DoIP — joined by a gateway with a zone-based firewall, diagnostic filter and anomaly detector. Ten attacks, each run permissive versus hardened.

The demo that lands. The pivot: compromise a door module on the LIN bus and try to reach the brake ECU. Without zone policy, all the way. With it, you stop at the gateway.

Python 10 phases · 22 criteria · a week of evenings
PROJECT 06

ECU Firmware Validation Pipeline

FreeRTOS in C on an emulated Cortex-M running a UDS server behind an ISO-TP reassembler, with eight planted and documented vulnerabilities — wrapped in static analysis, sanitizers, coverage-guided fuzzing, SBOM generation and CVE scanning.

The demo that lands. The tool-comparison matrix: every planted bug against every tool, found or missed. One is chosen precisely because nothing catches it.

C + Python 10 phases · 22 criteria · two weeks of evenings

Traceability

Every project names the document it implements

Naming ISO/SAE 21434 Clause 15 is a credibility multiplier. Naming AUTOSAR R20-11 in 2026 undoes it in one sentence. So the editions are not recalled — they are pinned in the manifest, dated, and enforced.

The standards register records, for each of 27 documents, the edition to cite, when it was last checked and against what. The build fails if a project cites a standard that is not declared, cites one marked superseded, or cites nothing at all.

What moved

The six specifications were drafted against an earlier snapshot. These are the five corrections that matter most — each one checkable in seconds by someone who works in the field.

WasIs
ML-DSA as the post-quantum firmware-signing rootCNSA 2.0 names LMS or XMSS for firmware signing. ML-DSA-87 is for general signatures.
UDS security access is 0x27 seed/keyISO 14229-1:2020 added 0x29 Authentication; ISO 15765-4 deprecates 0x27 for new designs.
AUTOSAR R20-11 / R21-11R25-11, released December 2025.
SBOM required by UN R155 or ISO/SAE 21434Neither mandates one. The EU Cyber Resilience Act does — the first binding SBOM mandate in law.
SAE J3101 is in developmentPublished February 2020.

Try it

Runs thirty seconds after cloning

The repository tooling is deliberately zero-dependency — Python 3.11+ and nothing else. No virtualenv, no install step, no dependency to resolve. 

# clone and look around
git clone https://github.com/michealswolski/\
Automotive-ECU-Cybersecurity-Lab-.git
cd Automotive-ECU-Cybersecurity-Lab-

make status   # specified / building / built
make check    # every consistency rule + tests
# build one of the projects
cd projects/secure-boot-chain-simulator
claude        # then paste prompts/kickoff.md

# one phase at a time. run the demo after
# each one. if you can't explain a file,
# ask about that file before moving on.

labctl keeps the repository honest about itself: one manifest describes the six projects, every table is rendered from it, and CI fails if any of them drifts — including if a project is marked complete while its own acceptance checklist still has unchecked boxes. How the tooling works ↗
